# Mower 排班工作台兼容移植设计

日期：2026-09-02

目标分支：`mode/shift-run`

状态：待用户审阅

## 1. 目标

在跑单版收益计算器中建立一套接近 Mower 排班编辑页的完整工作台。它需要覆盖主排班、副排班、设施拖拽、干员选择、跨设施组合、替补顺序、触发条件、任务覆盖、全局换人、策略设置、校验、JSON 导入导出和排班图导出，并把排班变化接入现有心情与长期产出模拟。

本设计采用“兼容层式移植”：排班工作台拥有独立的数据模型和交互层，现有收益算法继续作为计算核心。两者通过有类型、可测试的适配器通信。不得把 Mower 的设备控制、截图识别或后端任务执行代码引入计算引擎。

## 2. 成功标准

完成后应满足以下条件：

1. 熟悉 Mower 的用户无需重新学习设施图、主副表、干员、组合、替补、触发器和任务的基本操作。
2. Mower 排班 JSON 中与排班页相关的数据可以导入、编辑并再次导出；无法参与收益模拟的字段仍无损保留。
3. 工作台中生效的排班能够稳定转换成现有计算器输入，并给出长期日平均产出、心情变化和换班记录。
4. 房间交换会同步更新所有主副排班、触发条件和任务中的房间引用。
5. 非法排班不会悄悄产生收益：界面指出具体位置和原因，严重冲突时阻止汇总，但仍允许继续编辑。
6. 当前跑单版已有算法回归测试保持通过；标准版分支不被修改。

## 3. 范围

### 3.1 本次范围

- Mower 排班页的核心视图和使用逻辑。
- 主排班与任意数量的有序副排班。
- 九个产出设施、控制中枢、四个宿舍、会客室、加工站、办公室、训练室和活动室的统一设施图。
- 设施类型、等级、产品和干员席位编辑。
- `Free`、`Current` 和空席等 Mower 特殊席位值。
- 干员检索、拼音检索、技能摘要、已占用状态、跨设施组合和有序替补列表。
- 副排班触发器、任务覆盖和排班策略。
- 全局换人、校验、导入导出和排班图导出。
- 将时间、心情和房间状态触发器接入长期模拟。
- 跑单版的订单生成前换入逻辑继续由现有跑单算法负责，不把它伪装成普通副排班切换。

### 3.2 不在本次范围

- ADB、截图识别、点击操作、Mower 后端服务、定时启动游戏和材料加工等设备自动化。
- Mower 其他页面、左侧全应用导航和非基建功能。
- 修改标准版分支。
- 在本阶段自动搜索最优排班；本工作台先提供后续优化器所需的稳定数据边界。

## 4. 技术路线

选择“选择性移植 + 兼容模型 + 计算适配器”，不直接复制 Mower 的整个前端工程，也不完全凭视觉重写。

- 可复用 Mower `Plan.vue`、`PlanEditor.vue`、`SlickOperatorSelect.vue`、`TriggerDialog.vue`、`TriggerEditor.vue`、`TriggerString.vue` 和 `TaskDialog.vue` 的布局、交互和必要实现片段。
- 使用 Naive UI 获得与原页面一致的选择器、对话框、动态输入和消息反馈；使用 Pinia 管理工作区；使用 `pinyin-pro` 支持检索；使用轻量拖拽库实现副表排序、替补排序和设施交换；使用 `html-to-image` 导出排班图。
- 不引入 Mower 的路由、HTTP API、全局配置仓库和自动化后端依赖。
- 复制或改写的实质性 Mower 代码必须保留 MIT 许可。仓库新增第三方声明，注明 `Copyright (c) 2021 Nano` 和来源路径。

## 5. 架构

系统分为五个边界清晰的模块：

### 5.1 `workbench/model`

定义排班工作区的持久化结构、默认值、迁移和规范化。它不依赖 Vue，也不依赖计算引擎。

顶层结构如下：

```ts
interface RosterWorkspace {
  schemaVersion: 8
  name: string
  mainPlan: RosterPlan
  subPlans: RosterSubPlan[]
  selectedPlanId: 'main' | string
  simulation: SimulationSettings
  compatibility: MowerCompatibilityEnvelope
}
```

`compatibility` 保存来源版本和当前程序不理解的 Mower 字段。导出时将这些字段与已编辑字段合并，避免导入后丢失信息。

### 5.2 `workbench/store`

Pinia 工作区仓库负责编辑命令和撤销所需的原子变化，包括：选择排班、创建/复制/重命名/删除/排序副表、交换房间、设置席位、设置组合、调整替补顺序、全局换人和导入。组件不得直接执行跨排班同步操作。

房间交换是一个事务：同时交换主表和全部副表对应房间，递归改写触发器中的房间值，并交换任务映射的键。任一步失败则不提交变化。

### 5.3 `workbench/compat`

负责 Mower JSON 的导入与导出：

- 导入分为语法解析、版本识别、字段规范化、干员名称解析和语义校验。
- 干员名称转换为内部稳定 ID；导出 Mower 格式时再恢复名称。
- 未识别干员、房间、策略或触发器不会被删除，而是标记为兼容性警告并保留原始值。
- 本项目原有 `AppConfig` 通过单独迁移器升级为 `RosterWorkspace`，不覆盖用户原文件。

### 5.4 `workbench/simulation-adapter`

这是工作台与算法之间的唯一接口：

```ts
compileWorkspace(
  workspace: RosterWorkspace,
  horizonHours: number,
): CompiledRosterScenario
```

它负责把 Mower 房间 ID、席位、组合、替补和策略转换为事件驱动的计算场景。现有 `calculate`、效率规则、全局资源、心情规则和跑单订单算法不读取 UI 状态。

### 5.5 `engine/roster-timeline`

在现有 `shiftRoster` 之上增加多排班时间线。它维护当前排班、每名干员的位置与心情、宿舍恢复、替补候选、组合状态和下一事件时间。效率计算器只接收某一时间片的有效 `AppConfig`，随后按时间片累计产出。

## 6. 数据模型

### 6.1 房间标识

工作台使用 Mower 的稳定房间标识：

- 产出设施：`room_1_1` 至 `room_3_3`。
- 控制中枢：`central`。
- 宿舍：`dormitory_1` 至 `dormitory_4`。
- 会客室、加工站、办公室、训练室：`meeting`、`factory`、`contact`、`train`。
- 活动室：`gaming_1` 至 `gaming_3`。

产出设施在转换到现有引擎时按图中从上到下、从左到右的固定顺序映射为 `B1` 至 `B9`。任何业务规则不得依赖 `B1` 表示某一种设施。

### 6.2 排班

`RosterPlan` 是完整快照，不是相对主表的差量：

```ts
interface RosterPlan {
  id: string
  name: string
  facilities: Record<MowerRoomId, RosterFacility>
  policies: RosterPolicies
}
```

完整快照便于预览、独立校验和稳定导入。复制主表创建副表时产生新的 ID，但保持房间和席位内容。

### 6.3 设施与席位

```ts
interface RosterFacility {
  type: FacilityType | ''
  level: 1 | 2 | 3 | 4 | 5
  product?: ProductType
  slots: RosterSlot[]
}

interface RosterSlot {
  occupant: { kind: 'operator'; operatorId: string }
    | { kind: 'free' }
    | { kind: 'current' }
    | { kind: 'empty' }
  groupId: string | null
  replacements: string[]
}
```

替补是有序列表。模拟换班时选择第一个心情足够、未在别处工作且不违反唯一性约束的候选人。旧版单一 `operatorBackups` 转换为长度为一的列表。这样既保留用户当前“一人一替补”的习惯，也兼容 Mower 的多级候补。

### 6.4 组合

组合属于整个工作区，不属于单个房间。相同 `groupId` 的席位可以分布在不同设施。组合中的当前在岗成员任一达到离岗条件时，整个组合在同一时间点离岗；每个席位再按自己的有序替补寻找接班人。若组合不能完整接班，按策略选择：

- 默认严格模式：此次组合换班不执行，并报告阻塞原因。
- 用户明确允许空席时：能够接班的席位执行，其余空缺。

初始实现采用严格模式，避免通过部分组合制造错误的联动效率。

### 6.5 排班策略

每个主副排班独立保存 Mower 风格策略：`rest_in_full`、`exhaust_require`、`workaholic`、`resting_priority`、`refresh_drained`、`free_blacklist`、`ope_resting_priority`，以及与菲亚梅塔恢复目标有关的顺序。

策略分为三类：

- 可计算：直接影响离岗阈值、宿舍恢复、替补优先级或回岗顺序。
- 仅自动化：保留并显示“当前不参与收益模拟”。
- 未识别：原样保留并显示兼容性警告。

UI 必须在字段旁明确标注其类别，不能让用户误以为所有 Mower 自动化策略都已进入收益公式。

## 7. 副排班、触发器和任务

### 7.1 副排班

副排班是有序列表。顺序同时表示同一时机出现多个真条件时的优先级：从上到下选择第一个满足条件的副表。没有副表条件成立时回到主排班。

为防止一个时间点反复切换，排班选择在一次触发周期内只提交一次；切换后重新计算下一事件，不在同一阶段递归触发。

### 7.2 触发时机

保留 Mower 四种时机，并为模拟器定义确定语义：

- `BEGINNING`：时间片开始、处理本时刻离岗事件之前。
- `BEFORE_PLANNING`：处理离岗、组合离岗和宿舍恢复事件之后，安排接班之前。
- `AFTER_PLANNING`：接班安排完成之后，计算新时间片效率之前。
- `END`：时间片产出累计完成之后。

### 7.3 触发表达式

触发器存储为类型化语法树，同时能够与 Mower 的 `{ left, operator, right }` 结构互转。第一阶段支持：

- 布尔运算：`and`、`or`。
- 比较：`==`、`!=`、`>`、`<`、`>=`、`<=`。
- 算术：`+`、`-`。
- 干员状态：是否工作、是否休息、当前位置、当前心情。
- 全局时间：模拟时间和 Mower `party_time` 对应值。
- 常量：数字、布尔值、字符串和房间 ID。

禁止使用 JavaScript `eval` 或动态执行导入字符串。无法安全解析的表达式原样保存，但在模拟中视为不可执行并显示错误。

### 7.4 任务

副排班任务是按房间定义的局部席位覆盖，用于在副表生效时表达 `Free`、`Current` 或指定干员列表。任务不会调用 Mower 后端。

- `Current` 保留切换前该席位的实际干员。
- `Free` 由当前策略从可用干员中选择；尚未实现自动优选前，优先采用该席位替补列表，否则保持空席并给出提示。
- 指定干员按任务顺序写入对应房间。
- 技能专精、加工材料等非排班任务可导入、编辑和导出，但标记为“不参与收益模拟”。

## 8. 长期模拟数据流

1. 用户编辑工作区；每次操作先经过规范化和即时校验。
2. 用户点击计算，工作区被冻结为不可变快照。
3. 兼容层解析名称和特殊席位，模拟适配器生成初始排班及触发规则。
4. 时间线从 `t=0` 开始，选择当前有效排班，并寻找下一个事件：心情阈值、宿舍恢复完成、显式任务时间、触发器状态变化或模拟终点。
5. 在两个事件之间，当前有效房间转换为 `AppConfig`，调用现有效率和产出规则计算该时间片收益。
6. 事件点更新心情、位置、组合和替补，再按四个触发阶段评估副排班。
7. 所有时间片相加后除以模拟天数，得到长期日平均产出；同时输出每次排班切换、换人和无法接班的原因。

无人机容量固定默认 235，但长期模拟仍按充能速率、消耗和容量截断逐时间片计算。跑单在每个贸易订单生成点临时应用但书与龙舌兰效果，随后恢复当前排班人员；它不消耗一个副排班切换事件。

## 9. UI 设计

工作台采用 Mower 排班页的纵向结构，宽屏以约 980px 的内容主列为基准，小窗口允许横向或纵向滚动，不缩小到无法操作。

### 9.1 顶部工具栏

包含副表前移/后移、主副表选择、重命名、新建、复制、删除、触发条件、任务、全局换人、校验、导入、导出 JSON 和导出图片。破坏性操作需要确认；导入先预览问题，再决定替换当前工作区。

### 9.2 基建排班图

- 左侧为三行三列产出设施；右侧排列控制中枢、四宿舍和功能设施。
- 产出设施可拖拽交换，房间颜色和产品图标与 Mower 含义一致。
- 每个设施卡显示名称、产品和当前干员；组合使用稳定色条标识。
- 选中设施后，下方显示设施类型、等级、产品及所有席位。

### 9.3 席位编辑

每一行依次显示主力、组合和替补列表。干员选择器采用 Mower 的紧凑弹层：支持名称/拼音检索、设施类型筛选、技能摘要、已使用位置提示和禁止冲突选择。替补以可排序标签显示，可直接添加、移除和拖动优先级。

### 9.4 策略和报告

排班策略紧随编辑器，不放入远离排班图的独立页面。计算按钮和电力状态保持可见。结果报告与编辑器分栏或上下排列，但不把算法参数混回每个设施卡。

### 9.5 响应式要求

- 大于 1200px：编辑器与结果并列。
- 768px 至 1199px：上下排列，工具栏自动换行。
- 小于 768px：设施图保持最低可用宽度并置于可滚动容器，主要操作常驻顶部；对话框不超出视口。
- 键盘焦点、错误标识和颜色对比必须可辨认；组合不能只靠颜色识别，还要显示名称或缩写。

## 10. 校验与错误处理

校验分为三个等级：

- 错误：重复在岗、主力与替补冲突、房间容量超限、等级/设施类型非法、电力不足、无法解析且可能改变排班的触发器。阻止收益汇总。
- 警告：空替补、兼容字段未参与模拟、任务引用未知干员、副表永远不可达。允许计算可确定部分。
- 提示：当前策略可能造成无人机溢出、长时间空席或赤金供需失衡。

所有问题都包含排班 ID、房间 ID、席位索引和可读消息。导入错误不得覆盖当前工作区。自动保存使用新命名空间，并保留最近一次可解析快照；浏览器存储损坏时恢复默认值，同时提供损坏内容下载。

## 11. 迁移

现有 schema v7 配置迁移到 schema v8 时：

1. 九个 `rooms` 按当前数组顺序映射到九个 Mower 房间。
2. `facilityOperatorIds`、控制中枢和宿舍人员进入对应设施席位。
3. `operatorGroups` 转成稳定 `groupId`；跨设施成员关系保持不变。
4. `operatorBackups` 转成每个主力席位的首个替补。
5. 现有心情、全局资源、无人机目标和模拟时长进入 `simulation`。
6. 迁移后立即执行校验；旧数据保留在单独的 legacy 存储键，不自动删除。

## 12. 测试策略

### 12.1 模型和兼容层

- 默认工作区和 schema 迁移快照测试。
- Mower JSON 导入/导出往返测试，包含未知字段。
- 房间交换同步更新主表、副表、触发器和任务。
- 全局换人覆盖主力和所有替补，不误改相似名称。

### 12.2 触发与时间线

- 四个触发时机的顺序测试。
- 同时满足多个副表时按顺序取第一个。
- 组合跨设施同步离岗及严格接班。
- `Current`、`Free`、多级替补和无法接班。
- 心情阈值、宿舍恢复和回岗形成多次循环。
- 不安全表达式不执行。

### 12.3 收益回归

- 现有制造、贸易、自动化、感知信息、赤金生产线、无人机和跑单测试全部保留。
- 同一固定排班通过旧 `AppConfig` 与新适配器计算时，效率和 24 小时产出一致。
- 使用用户提供的二赤金、三赤金样本验证设施效率。
- 长时间模拟按周期稳定，日平均值不随模拟起点或不必要分片发生漂移。

### 12.4 UI

- 组件测试覆盖主副表管理、设施选择、替补排序、触发器编辑、导入预览和错误定位。
- 在 1920×1080、1366×768 和窄窗口进行视觉快照与人工操作对照。
- 与 Mower 原排班页逐项核对布局、按钮、拖拽、选择器和对话框行为。

## 13. 实施分解

本设计按以下顺序实施，每一阶段都有独立验收点：

1. 工作区模型、v7 迁移、Mower 兼容读写和计算适配器骨架。
2. Pinia 工作区、顶部工具栏、完整设施图和设施事务交换。
3. Mower 式干员选择器、组合、有序替补和全局换人。
4. 主副排班、触发器、任务和策略编辑。
5. 多排班事件时间线及长期日平均收益接入。
6. 导出图片、响应式修正、许可声明和与 Mower 的视觉/交互验收。

阶段之间不得用未类型化的临时 JSON 直接连接 UI 和引擎。每一阶段必须先补充失败测试，再实现，并在合入下一阶段前运行完整测试、类型检查和生产构建。

## 14. 决策记录

- 采用完整快照副表，而非主表差量。
